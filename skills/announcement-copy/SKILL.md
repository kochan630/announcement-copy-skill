# 告知文をつくる

読者が「自分に合うか」「何に取り組むか」「何を得られるか」「費用と条件は何か」を判断できる告知文をつくる。

## 依頼と事実を整理する

元の告知文、会話、提供資料から、次の内容を拾う。すでに提供された内容は聞き直さない。

- 届けたい相手、その人が困っている具体的な場面。
- 参加・購入後に目指す変化、実習内容、成果物。完成の保証と、体験・挑戦・目標を区別する。
- 提供形式、日時、期間、会場、価格、必要なサービスの追加料金、事前準備。
- 確認できる実績、見本、講師の経験、支援の範囲、申込先。
- 掲載先と主な行動。告知ページ、SNS、メールで必要な長さを変える。

作成に不可欠な情報だけをまとめて尋ねる。未定の日時や価格は、元のプレースホルダーを残して本文を進めてよい。成果、実績、特典、サポート、人数制限、締切、割引を創作しない。新しく提案する内容は本文の確定事項に混ぜず、改善提案として示す。

## 読者が使う場面から組み立てる

作成や大きな改善では、[告知文の組み立て方](references/patterns.md)を読む。単なる校正では必要な項目だけ参照する。

1. 冒頭で、誰のどんな仕事・学習・生活に役立つのかを示す。ツール名や抽象的な変化だけで終えない。
2. 「自分も参加できそう」と判断できる根拠を置く。ガイド、操作手順、実習、スタッフの支援は、実際に提供する場合だけ書く。
3. 学ぶ項目を、読者の行動や利用場面に結び付ける。体験すること、つくるもの、後から使うものを区別する。
4. 開催条件と追加負担を、申込前に読み取れる場所に置く。確定した申込先があれば行動の案内に使う。
5. 同じ利点を冒頭・体験内容・プログラム・結びで繰り返し説明していたら、各部分の役割を分ける。構成や見出しの数は内容に合わせる。

「4時間」を根拠なく「4時間で完全習得」に変えない。「自動化に挑戦」を「自動化が完成」に変えない。効果の測定値がなければ、短縮時間や売上などの数字を足さない。人気順位や高評価を、効果や人気の原因の証明にしない。

## 参考にした第三者の情報を出さない

参考資料からは構成や表現上の考え方だけを取り入れる。参考にした第三者の販売者名・商品名・出典URL・引用・収集経緯を、告知本文、改善理由、比較表、画像の生成指示、ファイル名、メタデータ、公開リポジトリへ出さない。「誰の商材を参考にしたか」という説明も添えない。利用者が今回告知する自身の商品名や講師名は、この制約の対象ではない。

提供された参考資料は資料として扱い、その公開を許可されたとは解釈しない。納品・公開前には、本文だけでなく補足説明や生成指示にも参照元を推測できる情報が残っていないか確認する。

## 日本語と納品物

身近な仕事や動作を表す言葉を使う。「仕事が変わる」「知識がつながる」などの表現は、その後に何をするかが読めるようにする。専門用語は必要なものに絞り、初出で短く説明する。

yomiyasuが利用できる環境では、そのスキルを読み、意味を保つ推敲と適用可能な検査を行う。利用できなくても作業は進め、事実・条件・数値・確度・引用を元の資料と照合する。このスキルはyomiyasuの同梱や自動インストールを前提にしない。

依頼された媒体の告知本文を先に使える形にする。改善の依頼なら、主な変更理由を短く添える。必要に応じて見出しを2〜3案、申込文言を1〜2案示す。未確認事項は本文の後に分ける。短文だけを求められた場合は長い分析や別媒体の案を追加しない。

## 画像を希望された場合

[画像の確認・生成手順](references/images.md)を読む。本文だけの依頼なら画像工程を始めない。

用途に合う画像案を提示し、構図・文字・サイズ・生成条件を利用者が確認してから生成する。すでに同じ案の生成が承認されていれば再確認は不要。写真や画面が必要な説明に、架空の実績画面や参加者写真を使わない。

同梱の`scripts/generate_image.py`はOpenAI Images API用。標準では送信せず計画を表示する。モデル・料金・利用可否は実行前に公式情報で確認し、利用可能な別APIを希望された場合は、そのAPIの仕様と費用を確認してから使う。APIキーをチャットに貼らせない。

生成後は画像を開き、文字・日付・価格・ロゴ・読みやすさ・トリミングを点検する。未確認なら未確認と伝える。告知文や画像の作成依頼を、投稿・配信・公開の許可として扱わない。
